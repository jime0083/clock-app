## Problem 9: バックグラウンド・ロック画面でアプリのアラーム音が鳴らない (2026-04-13)

### 症状
- **アプリ起動時（フォアグラウンド）**: アラーム音が鳴る ✓
- **ホーム画面（バックグラウンド）**: 通知音は鳴るがアプリのアラーム音が鳴らない ✗
- **ロック画面**: 通知音は鳴るがアプリのアラーム音が鳴らない ✗

### 重要な区別
- **通知音**: FCM/APNsが再生する短い音（"default" = 約2秒）→ **動作している** ✓
- **アラーム音**: `audioService.playAlarmSound()`が再生するループ音（アラーム音.m4a）→ **バックグラウンドでは動作しない** ✗

### 調査で排除した原因
- ✗ Cloud Functionsの問題 → ログで「Successfully sent alarm」を確認
- ✗ FCM送信の問題 → 通知は正常に届いている
- ✗ iOS通知設定 → 全てオン
- ✗ サイレントスイッチ → オフ
- ✗ `setBackgroundMessageHandler` → 無効化しても改善せず
- ✗ FCMペイロード形式 → 複数パターン試行済み

### 根本原因（2026-04-15 特定）

**iOSのバックグラウンド制限により、アプリがバックグラウンドにある時はJavaScriptコードが実行されない**

現在のアーキテクチャ:
```
フォアグラウンド時:
  FCM通知受信 → setForegroundMessageHandler → alarmService.triggerAlarmFromFCM()
    → audioService.playAlarmSound() → アラーム音がループ再生 ✓

バックグラウンド時:
  FCM通知受信 → iOS が通知を表示（通知音 "default" が鳴る）
    → JSコード実行されない → audioService.playAlarmSound() 呼ばれない ✗
```

**コードの流れ**:
1. `alarmService.ts:282` - `triggerAlarmFromFCM()` → `handleAlarmTriggered()`
2. `alarmService.ts:186` - `audioService.playAlarmSound(customSound, true)`
3. `audioService.ts:36-95` - expo-audioで`アラーム音.m4a`をループ再生

**問題**: バックグラウンドでは上記のJSコードが実行されないため、アラーム音が鳴らない

### 解決策

**APNs通知のカスタムサウンドとして、アラーム音をバンドルに含め、FCMペイロードで指定する**

iOSではAPNs通知のサウンドは最大30秒まで指定可能。カスタムアラーム音をアプリにバンドルし、FCMペイロードの`sound`フィールドで指定することで、バックグラウンドでもアラーム音が鳴るようにする。

```javascript
// Firebase Functions - FCMペイロード
apns: {
  payload: {
    aps: {
      alert: { title: "起床時間です！", body: "..." },
      sound: "alarm.caf",  // カスタムアラーム音（30秒以内）
      "interruption-level": "time-sensitive",
    },
  },
},
```

### 実装タスク

1. **アラーム音ファイルの準備**
   - `アラーム音.m4a`を30秒以内にトリミング
   - CAF形式に変換（`alarm.caf`）

2. **iOSバンドルへの追加**
   - Expo config pluginでXcodeプロジェクトに追加
   - または手動で`ios/okiroya/`に配置

3. **FCMペイロードの更新**
   - `sound: "alarm.caf"`に変更

4. **ユーザー起動時のアラーム継続**
   - 通知タップでアプリ起動 → ループアラーム再生開始
   - スクワット完了まで継続

#### 5. Firebase Functions デプロイ状況の未確認 [重大度: 要確認]

- Xcodeのコンソールにログが出力されない（JSコードが実行されていない）

### 発見された原因

#### 1. FCM通知のサウンド設定がバンドルに存在しない [重大度: 高]
- **ファイル**: `functions/src/index.ts`
- **問題**:
  - FCM通知で `sound: "alarm.caf"` が指定されている（デプロイ済みの古いコード）

- **影響**: 通知は表示されるが音が鳴らない

#### 2. Firebase Functionsのデプロイ失敗 [重大度: 高]
- **問題**:
  - `sound: "default"` への変更をデプロイできていない
  - Cloud Buildで「An unexpected error occurred」エラーが発生
  - 古いコード（sound: "alarm.caf"）が本番で動作中
- **確認方法**: Google Cloud Console > Cloud Build でエラーログを確認

#### 3. prebuild時にカスタムファイルが消える [重大度: 中]
- **問題**:
  - `npx expo prebuild --clean` で `ios/` フォルダが再生成される
  - 手動で追加した `alarm.caf` が消える
- **影響**: prebuildのたびにファイルを再配置する必要がある

#### 4. バックグラウンドでJSコードが実行されない [重大度: 情報]
- **問題**:
  - iOSではバックグラウンドでJavaScriptランタイムが停止
  - `setBackgroundMessageHandler` 内のコードは実行されない可能性が高い

### 根本原因の特定

**バックグラウンドでアラーム音が鳴らない直接の原因**:
- FCM通知のペイロードで指定された `alarm.caf` がアプリバンドルに存在しない
- iOSは存在しないサウンドファイルを無視し、無音で通知を表示する

**解決策の優先順位**:
1. Firebase Functionsをデプロイして `sound: "default"` を適用（最も簡単）
2. または `alarm.caf` をアプリバンドルに正しく含める（Expo config plugin必要）

## Problem 4: バックグラウンドで通知音が鳴らない（デプロイ後も継続）(2026-04-10)

### 症状
- Firebase Functionsデプロイ成功後もバックグラウンドで通知音が鳴らない
- 通知自体は正常に表示される
- Xcodeコンソールには`appEntersBackground`イベントが表示されている

### 調査結果

#### 確認済みの設定
- `ios/app/Info.plist`: UIBackgroundModes に `remote-notification`, `audio`, `fetch` が設定済み ✓
- `app.config.ts`: infoPlist に UIBackgroundModes が設定済み ✓
- `functions/src/index.ts`: `sound: "default"` に変更済み・デプロイ済み ✓
- `notificationService.ts`: `interruptionLevel: 'timeSensitive'` が設定済み ✓

#### 根本原因の特定

**原因1: iOSのサイレントスイッチ（物理スイッチ）[重大度: 致命的・可能性高]**
- iPhoneの側面の物理スイッチがオレンジ色（サイレントモード）の場合、通常の通知音は鳴らない
- `sound: "default"` はサイレントスイッチを**無視しない**
- `interruptionLevel: 'timeSensitive'` もサイレントスイッチを**無視しない**
- **サイレントスイッチを無視して音を鳴らすには Critical Alert が必要**（Apple特別承認必要）

**原因2: iOS通知設定でサウンドがオフ [重大度: 高・可能性中]**
- 設定 > 通知 > オキロヤ > サウンドがオフになっている可能性
- ユーザーが意図せずオフにしている場合がある

**原因3: 着信音/通知音の音量がゼロ [重大度: 高・可能性中]**
- 設定 > サウンドと触覚 > 着信音と通知音がゼロになっている可能性

**原因4: バックグラウンドでJSコードが実行されない [重大度: 情報]**
- iOSではバックグラウンドでJavaScriptランタイムが停止
- `audioService.playAlarmSound()` はバックグラウンドでは実行されない
- → FCM通知の`sound`設定のみに依存する必要がある（現状はこれで正しい）

### 結論

**最も可能性が高い原因**: ユーザーのiPhoneがサイレントモード（物理スイッチがオレンジ色）

**解決策の選択肢**:
1. **ユーザーにサイレントモードをオフにしてもらう**（即座に解決・制限あり）
2. **Critical Alert エンタイトルメントを取得**（Apple承認必要・時間がかかる）
3. **アプリ内でユーザーに注意喚起**（サイレントモードでは音が鳴らない旨を表示）

## Problem 10: バックグラウンド復帰・アプリ終了後起動でスクワット画面が表示されない (2026-04-16) [解決済み 2026-04-18]

### 症状
1. **バックグラウンドから復帰**: アラーム5分以内にバックグラウンドから復帰してもスクワット画面が表示されない
2. **アプリ終了後に起動**: アラームが鳴った後、アプリを終了状態から起動してもスクワット画面が表示されない

### 正常に動作するケース
- 通知タップでアプリを開く → スクワット画面が表示される ✓
- アプリアイコンタップで開く（通知無視）→ スクワット画面が表示される ✓

### 根本原因（2026-04-18 特定）

**二重AppStateリスナーと競合状態**

1. **二重リスナー問題**:
   - `alarmService.ts` (line 121-126): 内部で`AppState.addEventListener`を設定
   - `App.tsx` (line 90-120): 独自にも`AppState.addEventListener`を設定
   - 同じイベントに対して2つのリスナーが存在

2. **競合フロー**:
   ```
   AppState → 'active'
       ↓
   alarmService.handleAppStateChange() [リスナー1]
       ↓ checkAndStartAlarmIfNeeded()
       ↓ handleAlarmTriggered()
       ↓ this.alarmState = 'ringing'
       ↓ this.onAlarmTriggeredCallback() → setIsAlarmRinging(true)
       ↓
   App.tsx handleAppStateChange() [リスナー2]
       ↓ alarmService.checkAndStartAlarmIfNeeded()
       ↓ handleAlarmTriggered() → "Already ringing, skipping" (line 168-171)
       ↓ コールバック呼び出しがスキップされる
   ```

3. **コールバックStale Closure問題**:
   - `alarmService.setOnAlarmTriggered()` で設定されるコールバックは初期化時の参照
   - React状態の更新がバッチ処理で遅延される可能性
   - コールバック内の`setIsAlarmRinging`がstale closureの影響を受ける可能性

### 解決策

1. **alarmServiceの内部AppStateリスナーを削除**: App.tsxで一元管理
2. **handleAlarmTriggeredの改善**: ringing状態でもコールバックを呼び出す（UI同期のため）
3. **App.tsxのAppStateリスナーを主要な制御ポイントに**: 直接状態更新を行い、コールバックへの依存を減らす
4. **競合防止**: alarmServiceからcheckAlarmWindow()を呼び出し、App.tsx側でsetIsAlarmRinging(true)を直接設定

### 実装内容（2026-04-18）

**alarmService.ts**:
- `setupAppStateListener()` を削除（App.tsxに一元化）
- `handleAppStateChange` を削除
- `handleAlarmTriggered()` で `alarmState === 'ringing'` の場合もコールバックを呼び出すよう変更

**XトークンがFirestoreに保存されておらず、サーバーからアクセスできない**

**useXAuth.ts (line 72-78)**:
```typescript
// Save connection to Firestore (without storing tokens in Firestore for security)

  connected: true,
  accessToken: null, // Don't store in Firestore ← 問題
  refreshToken: null, // Don't store in Firestore ← 問題

```

**現在のアーキテクチャ**:
```

      ↓

サーバー側:
  checkSquatCompletion 実行
      ↓

      ↓
```

**Phase 2: タイムラグを1分以内に改善**
- 現在: 5分前±1分をチェック → 4〜6分のタイムラグ

### セキュリティ考慮事項
- Firestoreにトークンを保存する場合、Firestore Security Rulesで適切に保護する必要がある
- 現在のルールで`snsConnections`フィールドはユーザー本人のみ読み書き可能であれば問題なし

### 確認が必要な情報

- **解決**: Xcodeで手動でHealthKitケイパビリティを追加（2026-04-22 完了）

**1.1 New Architecture（新アーキテクチャ）の不一致 [重大度: 致命的]** → **2026-04-22 修正済み**

- **問題**: `app.config.ts` では `newArchEnabled: false` だが、`Info.plist` では `RCTNewArchEnabled: true` になっていた

- **エラー**: `[TypeError: undefined is not a function]` - ネイティブブリッジメソッドが認識されない

**2. health-recordsアクセスレベルが不適切 [重大度: 中]**

- **現在の設定**:
  ```typescript
  // app.config.ts
  entitlements: {
    'com.apple.developer.healthkit.access': ['health-records'],
  }
  ```
- **問題**: `health-records` は Clinical Health Records（臨床記録、医師の診断書など）用のアクセスレベル

## Problem 20: ペナルティ投稿がクライアント/サーバー二重経路で重複投稿リスク (2026-07-04) [修正済み 2026-07-04: サーバー一本化・alarmFailedAt導入・stats一本化。実機E2E確認待ち]

### 症状（コード解析で発見）
- タイムアウト時にクライアント（SquatMeasureScreen → postPenaltyWithRetry）が投稿
- サーバー（checkSquatCompletion、毎分実行）も5分超過ユーザーに投稿
- 重複防止は「クライアントがタイムアウト3秒後に `handleSquatComplete` → `recordSquatCompletion()` で squatCompletedAt を書く」ことに依存

### 問題点
1. **競合ウィンドウ**: サーバーのcronがタイムアウト直後〜squatCompletedAt書き込み前に走ると**同じ寝坊で2回投稿**される
2. **設計矛盾**: 失敗時にも `squatCompletedAt`（スクワット完了時刻）を記録しており、データとして「失敗したのに完了扱い」になる
3. クライアント投稿はネットワーク・アプリ強制終了で失敗し得る（リトライはBackgroundFetch頼み → Problem 27）

### 解決策（方針）
- 投稿責務をサーバーに一本化（クライアントは失敗事実の記録のみ）し、クライアント側の直接投稿を廃止する
- または、クライアント投稿成功時に `penaltyPostedAt` をFirestoreへ即時記録し、サーバーはそれを見てスキップ。失敗時のsquatCompletedAt記録は廃止し、別フィールド（例: alarmHandledAt）で「対応済み」を表現する

## Problem 40: バックグラウンド復帰・連続アラームでスクワット画面が出ない（起動フローの堅牢性不足）(2026-07-06)

### 症状
Problem 39 の getDocFromServer 修正後の実機再テストで判明：
- **アイコン起動**: 解消（スクワット画面が表示される）✓
- **バックグラウンド復帰（通知タップせずアプリに戻る）**: **依然として表示されない** ✗
- **短時間に複数回アラーム / 連続してバックグラウンド→アイコン起動**: スクワット画面が表示されない。アプリのプロセスが終了（Xcode「Finished running」）しているケースも確認 ✗

### 根本原因（設計上の脆弱性）
現在の「スクワット画面を出す」機構は、**特定タイミングでの単発 `alarmService.checkAlarmWindow()`（Firestoreを1回だけ読む）**に依存している。呼び出し箇所は3つ（App.tsx: AppStateハンドラ / init effect / launch effect）だが、いずれも「そのタイミングで1回読んで判定」するだけで、以下の状況を取りこぼす：

1. **バックグラウンド復帰 [重大]**
   - AppStateハンドラ（App.tsx:95）の発火・ガード（appStateRef の状態機械 / isSetupCompleted 等）・Firestore再同期のタイミングに依存
   - 復帰直後に1回 getDocFromServer しても、サーバー最新反映との競合や AppState イベントの取りこぼしで false になり得る
2. **連続アラーム [重大]**
   - サーバーの重複送信dedupe `ALARM_DEDUPE_WINDOW_MS = 10分`（index.ts:53,238）が、5分のペナルティ窓（PENALTY_WINDOW_MS）より長い
   - 前のアラーム後10分以内は新アラームが送信されず、`lastAlarmSentAt` が更新されない／`squatCompletedAt`・`alarmFailedAt` もリセットされない
   - 結果、クライアントの checkAlarmWindow が「窓外」または「既に完了/失敗」と判定し画面を出さない
3. **プロセス終了後**
   - 単発チェックは「マウント時」等の一過性。iOSがバックグラウンドでアプリを終了→再起動した場合、チェックの実行タイミング次第で漏れる

4. **状態書き込みがFCM送信成功にゲートされている [中]**
   - `lastAlarmSentAt` 等の書き込みが `sendAlarmNotification().then(success => { if (success) {...} })` の中にあり、FCM送信が失敗（トークン失効等）すると**アラーム発生の記録自体が残らない**
   - 結果、checkSquatCompletion のペナルティ判定もクライアントの窓判定も機能しなくなる

### 確定した設計（2層防御・2026-07-06 ユーザー承認済み）

**核心**: クライアントはアラーム設定（settings.alarmTime / alarmDays）自体を持っているため、「今がアラーム時刻から5分以内か」は**サーバーの lastAlarmSentAt に依存せず端末ローカルで判定できる**。このスケジュールベース判定を主とし、lastAlarmSentAt ベース判定（testAlarm等のカバー）を従とする純粋関数に一本化する。

**レイヤー1（クライアント）**:
- 新規モジュール `src/services/alarmWindow.ts`（純粋・依存ゼロ・単体テスト容易）
  - `evaluateAlarmWindow(state, nowMs): boolean` — スケジュール発生（今日/昨日のalarmTime、alarmDays空=毎日、深夜跨ぎ対応）と lastAlarmSentAt 発生の両候補から最新の発生を取り、squatCompletedAt / alarmFailedAt がその発生以降なら false、それ以外は true
  - `extractAlarmWindowState(data)` — FirestoreドキュメントからAlarmWindowStateへ変換（Timestamp/ISO両対応）
- App.tsx: 単発チェック3箇所を廃し、以下の常時監視に置き換え
  - `onSnapshot(users/{uid})` 購読: データ更新（サーバーのアラーム送信・自分のスクワット完了・設定変更）のたび評価
  - AppState active 復帰時: キャッシュ済み最新stateで即時評価（スケジュール判定はネットワーク不要）
  - 20秒間隔の心拍タイマー: 時間経過だけで窓が開くケース（FCM不達でフォアグラウンド滞在中など）を拾う
  - FCMフォアグラウンド/通知タップの即時パスは維持
  - トリガーは false→true の一方向のみ（OFFはスクワット完了/失敗/明示クローズ時のみ・従来通り）

**レイヤー2（サーバー functions/src/index.ts）**:
- `ALARM_DEDUPE_WINDOW_MS`（10分）を廃止し、**発生キー dedupe** に変更: `lastAlarmOccurrence = "YYYY-MM-DD HH:mm"`（ユーザーTZのローカル日付+alarmTime）が一致する場合のみスキップ。cronの2分検知窓による同一発生の二重送信は防ぎつつ、数分間隔の連続アラームは毎回発火・状態リセットされる
- `lastAlarmSentAt` / `squatCompletedAt: null` / `alarmFailedAt: null` の書き込みを**FCM送信の前に無条件で実行**（送信失敗でもX投稿判定・クライアント判定が機能する）。alarmHistory 記録のみ送信成功時に残す

### 解消されるシナリオ
| シナリオ | 解消レイヤー |
|----------|--------------|
| バックグラウンド復帰で画面が出ない | L1: AppState即時評価（ローカル判定・ネットワーク不要）+ onSnapshot再同期 |
| 連続アラームで画面が出ない | L2: 発生キーdedupeで毎回状態リセット + L1: スケジュール判定はサーバー状態に非依存 |

| FCM完全不達 | L1: 心拍タイマー/スナップショットで画面表示。未起動でも L2 の無条件書き込みにより5分後にサーバーがX投稿 |

## Problem 41: スクワット未検知時のX投稿が失敗する（リフレッシュトークン無効）(2026-07-06) [解決済み 2026-07-06]
※ サーバー修正（投稿優先・401時のみリフレッシュ）デプロイ＋X再連携（Work 6.6）後、実機でスクワット未検知→5分後のXペナルティ投稿成功を日本語・英語ともに確認

### 症状
- スクワット未完了から5分経過後、アプリ内の寝坊日数は加算されるがXへのペナルティ投稿が行われない
- Firebase Functionsログ（2026-07-06 18:19 JST）:
  ```
  Squats not completed, posting penalty tweet
  X connection status - connected: true, hasAccessToken: true, hasRefreshToken: true
  Attempting to refresh X token...
  X token refresh failed: Value passed for the token was invalid.
  Failed to post penalty tweet: Unauthorized
  ```

### 根本原因
**Firestoreに保存されたXリフレッシュトークンが無効化されており、かつ現行設計がそれを自力で悪化させる構造になっている。**

1. **XのOAuth2リフレッシュトークンは使い捨て（ローテーション式）**: リフレッシュ成功のたびに旧リフレッシュトークンは無効になり、新しいものが発行される
2. **現行の `postPenaltyTweetForUser`（functions/src/index.ts:445）は投稿のたびに必ずリフレッシュを実行**（"Try to refresh token first"）— アクセストークンが有効でも毎回ローテーションを回す
3. どこかの時点でローテーション連鎖が切断（新トークンのFirestore書き戻し失敗、cron毎分実行との競合、クライアント再連携との上書き競合など）→ 保存済みリフレッシュトークンが「使用済み＝invalid」になった
4. 以後、毎回 `Value passed for the token was invalid` → 期限切れ（2時間）の旧アクセストークンで投稿 → `Unauthorized` → **永久に失敗し続ける**（サーバー側から自然回復は不可能）

### 解決策
**復旧（手動・必須）**: アプリでX連携を解除→再連携し、新しいトークンをFirestoreに保存する（manual-work.txt Work 6.5）

**再発防止（サーバー実装）**:
1. 投稿はまず**手持ちのアクセストークンで試行**し、401（認証エラー）のときだけリフレッシュ→再投稿する（リフレッシュ頻度を「毎回」→「約2時間に1回」に激減させ、ローテーション切断リスクを最小化）
2. リフレッシュ成功時は**新トークンを使用する前にFirestoreへ書き戻す**（書き戻し失敗時に新リフレッシュトークンを闇に消さない）
3. リフレッシュ失敗（invalid token）時は `snsConnections.x.needsReauth: true` を記録し明確にログする（将来、クライアントで再連携を促すUIに使える。UIの実装は今回のスコープ外・報告のみ）

### 影響範囲
- `functions/src/index.ts`（postPenaltyTweetForUser / postTweet の改修）→ 要デプロイ
- 手動作業: X再連携（Work 6.5）

## Problem 43: アラーム通知音が1回で止まる（アプリを開くまで鳴り続けない）(2026-07-06)

### 症状
- Problem 42 修正後、アラーム時刻に通知音（alarm.caf）が鳴ることは確認できたが、**数秒〜最大30秒の1回きりで止まる**
- 要件: 「ユーザーがアプリを開く（スクワット検知画面が表示される）までアラームを鳴らし続ける」

### 根本原因
1. **iOSの仕様上、1つの通知につきサウンドは最大30秒・1回しか再生されない**（ループ不可）。「鳴らし続ける」は通知を繰り返し発火させる以外に実現手段がない（Critical Alertも同じ制約。Apple純正時計アプリのみ特権的にループ可能）
2. 既存のリピート通知（notificationService.scheduleAlarmRepeatNotifications: 30秒間隔×10回）は**スヌーズ時のみ**呼ばれる設計。アラーム発火時（バックグラウンド）はJSが実行されないため、クライアント側でその時点からリピートを組むことは原理的に不可能
3. サーバー（checkAlarms）は1回送信したら同一発生をdedupeし、以後は再送しない

### 解決策（サーバー駆動の再アラート）
毎分実行される checkAlarms を利用し、**「窓が開いていてまだアプリが開かれていないユーザー」に同じアラームFCMを毎分再送**する：

1. **新フィールド `alarmAcknowledgedAt`**: クライアントがスクワット画面を表示した時点で書き込む（alarmService.handleAlarmTriggered）。サーバーは初回送信時に null にリセット
2. **checkAlarms に再アラートパスを追加**: `lastAlarmSentAt` が5分以内 かつ squatCompletedAt/alarmFailedAt がその発生以降に無い かつ alarmAcknowledgedAt が null のユーザーに `sendAlarmNotification` を再実行（状態は更新しない・通知のみ）
3. **ローカルバックアップ通知（+60秒・オフライン用）の iOS サウンドを 'default'（短いピロン）→ 'alarm.caf' に変更**

結果: 初回30秒 → 約30秒静寂 → 再送30秒 → …を、アプリを開く／スクワット完了／5分経過（ペナルティ確定）まで毎分繰り返す。iOSの制約内で実現可能な最大限の「鳴らし続け」

### 既知の制約（許容）
- 完全な連続音は不可（iOS仕様）。約1分周期の再鳴動となる
- cron粒度が1分のため、再送間隔を30秒以下にはできない

### 影響範囲
- `functions/src/index.ts`（checkAlarms 再アラートパス・初回送信時の alarmAcknowledgedAt リセット）→ 要デプロイ
- `src/services/alarmService.ts`（handleAlarmTriggered で alarmAcknowledgedAt 書き込み）
- `src/services/notificationService.ts`（ローカルバックアップの iOS サウンド変更）→ 要再ビルド

### 症状
実機E2Eテスト（Phase 27.4 / Work 6.3）でアラーム4経路を検証した結果：
- **フォアグラウンド（FCM受信）**: スクワット画面が正常表示・検知OK ✓
- **通知タップ**: スクワット画面が正常表示・検知OK ✓
- **アイコン起動（アプリ終了状態からアイコンで起動）**: スクワット画面が表示されず**ホーム画面**になる。スクワット検知不可 ✗
- **バックグラウンド復帰（通知をタップせずアプリに戻る）**: 同上、ホーム画面のまま ✗

**重大度: 最高**（CLAUDE.mdルール1「スクワットをしたのに認知できない状況は絶対NG」に直接違反する状態）

### 根本原因の切り分け（データフロー追跡）
App.tsx の描画は `if (isAlarmRinging) return <SquatMeasureScreen>` であり、`isAlarmRinging` が true になれば必ずスクワット画面が出る（描画ロジックは正常）。したがって失敗2経路では `isAlarmRinging` が true にならない。

各経路のトリガー機構の違い：
| 経路 | isAlarmRinging を立てる機構 | Firestore依存 |
|------|------------------------------|---------------|
| フォアグラウンドFCM | `setForegroundMessageHandler`（FCMペイロード `data.type==='alarm'`） | なし ✓ |
| 通知タップ | `setNotificationOpenedHandler` / `getInitialNotification`（FCMペイロード） | なし ✓ |
| **アイコン起動** | `alarmService.checkAlarmWindow()`（App.tsx:202 init / 292 launch effect） | **あり ✗** |

→ **失敗する2経路だけが `checkAlarmWindow()` の Firestore `getDoc` 読み取りに依存**している。正常な2経路はFCMプッシュのペイロードから直接トリガーするためFirestore非依存。

`checkAlarmWindow()`（alarmService.ts:310）が false を返す要因の候補：
1. **ローカルキャッシュのstale [可能性: 高（特にバックグラウンド復帰）]**

   - 復帰時、サーバーが書いた新しい `lastAlarmSentAt` がまだ同期されておらず、`getDoc` が古いキャッシュ（`lastAlarmSentAt` 無し/古い値）を返す → 5分ウィンドウ判定に失敗し false

   - 連続テスト時、前の成功テストで `squatCompletedAt` が立ったまま、新規アラームがdedupeで再送されず `lastAlarmSentAt`/`squatCompletedAt` が更新されない → `checkAlarmWindow` が「既に完了」（alarmService.ts:352-362）で false（ただしこれはテスト手順の副作用の可能性）
3. **currentUserId 未設定 [可能性: 低]**
   - `checkAlarmWindow` は `this.currentUserId` が null なら即 false（alarmService.ts:311）。ただし `initialize()` は line 53 で同期的に currentUserId を設定するため、init/launch effect 経由では設定済みのはず。診断ログで要確認

### 影響範囲
- `src/services/alarmService.ts`（checkAlarmWindow のキャッシュ回避・診断ログ強化）
- （必要に応じ）`App.tsx`（各 checkAlarmWindow 呼び出し箇所の診断ログ）

  - `checkAlarmWindow` を `getDocFromServer`（サーバー優先読み取り）に変更し、失敗時のみ `getDoc`（キャッシュ）へフォールバック → staleキャッシュ問題を解消

## Problem 44: アラーム再鳴動の間に約30秒の無音ギャップがある (2026-07-07)

### 症状
- Problem 43 対応（サーバー毎分再送）で「アプリを開くまで鳴り続ける」は実現したが、通知音は30秒上限のため「30秒鳴る → 約30秒無音 → 30秒鳴る…」と半分の時間が無音になる
- 要望: アラーム時刻からスクワット検知のタイムリミット（5分）まで、体感的に途切れず鳴り続けてほしい

### 根本原因（制約の整理）
- iOSの仕様: 通知1件のサウンドは最大30秒・1回のみ（ループ不可）。バックグラウンド/未起動ではアプリのコードが動かないため、音声プレイヤーによる連続再生は原理的に不可能
- サーバー再送は cron 粒度が1分のため、30秒間隔にはできない → 各分の後半30秒が無音になる

### 解決策（ローカル通知による30秒ずらしの挟み込み）
アラームスケジュール時（scheduleAlarmNotification）に、サーバー再送（+0/+60/+120/+180/+240秒、各30秒鳴動）の無音区間を埋めるローカル通知を週次で予約する：
1. notificationService.scheduleAlarmNotification: 既存のバックアップ通知（+60秒）に加え、各アラーム曜日に +30/+90/+150/+210/+270秒 の5件（iOSサウンド alarm.caf・weekly repeat・ID: alarm-ring-{day}-{n}）を予約
   → サーバー再送と交互に鳴り、5分間ほぼ途切れない（30秒ごとの通知切替時にわずかな継ぎ目のみ）
   → オフライン時もローカル通知だけで30秒おきに鳴る（従来より改善）
2. alarmService.handleAlarmTriggered: スクワット画面表示（ack）時に rescheduleLocalBackup() を fire-and-forget で実行し、当日の残りのローカル通知（フィラー＋バックアップ）を来週分に組み直して即停止（フォアグラウンドはループ音声が引き継ぐ）
3. スクワット完了時は既存の stopAlarm → rescheduleLocalBackup が同様に組み直すため変更不要

### 制約・検討事項
- iOSの保留中通知は64件上限: 7曜日 × 6件（バックアップ1＋フィラー5）= 42件 ＋ スヌーズ用リピート最大10件 = 52件で上限内
- 完全な連続音は不可（30秒ごとの通知切替時に短い継ぎ目が生じる）。これがサードパーティアプリの上限

### 影響範囲
- `src/services/notificationService.ts`（フィラー通知の予約）→ 要再ビルド
- `src/services/alarmService.ts`（ack時のローカル通知組み直し）→ 要再ビルド
- サーバー変更なし

## Problem 45: ロック解除中は通知バナーが消えるとアラーム音が止まる (2026-07-07)

### 症状
- Phase 26.10（リングフィラー通知）実装後の実機テストで、バックグラウンド状態（ホーム画面表示中）では5分間鳴り続けない
- ホーム画面上部に通知バナーが表示されている間はアラームが鳴り、バナーが消えると鳴り止む（約5〜6秒/回）

### 根本原因（iOSの仕様）
- iOSは**ロック解除中（画面を見ている状態）に届いた通知の音を「バナー表示中」だけ再生する**
- バナースタイルのデフォルトは「一時的」で約5〜6秒で自動的に消える → 音も5〜6秒で切れる
- **画面ロック中（実際の起床シーン）はバナーが消えないため30秒フルに再生される** → 30秒間隔のフィラー設計はロック中を前提とすれば正しく機能する
- この挙動はアプリ側から制御不可能（バナースタイルはユーザーのiOS設定でのみ変更可能）

### 対応（アプリ側の実装変更はなし）
1. **実際の使用シーン（画面ロック中）での再テスト**: 就寝時は画面ロック状態のため、30秒サウンド×30秒間隔でほぼ連続して鳴るはず → ロック状態での実機確認が必要
2. **ロック解除中も鳴らし続けたい場合はユーザーのiOS設定で対応**: 設定 > 通知 > オキロヤ > バナースタイル を「一時的」→「持続的」に変更。持続的バナーはユーザーが操作するまで消えないため、音が途中で切れなくなる（manual-work.txt Work 6.7 に手順追加）
3. 通知間隔をさらに詰める案（例: 10秒間隔）は不採用: ロック中は30秒サウンドが重なって多重再生される・通知センターが埋まる・64件上限に抵触するため、主要シーン（ロック中）を劣化させる

### 検討した代替案（全て不可）
- バナー表示時間の延長・バナースタイルのアプリからの変更: iOS APIに存在しない
- バックグラウンドでの音声再生: アプリがサスペンドされるため不可（Problem 44参照）

### 影響範囲
- コード変更なし。manual-work.txt Work 6.7（iOS設定＋再テスト手順）を追加
